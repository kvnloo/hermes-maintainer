## What this actually is

Tek shipped the **self-hosted Linux gateway + Hermes Desktop** half of “a bot has a screen you can take over.”

Per-profile TigerVNC `Xvnc` (Unix socket 0600, no TCP) + Xfce under a private dbus session, a disk lease with optional fcntl, a server-side RFB input filter, ticketed `/api/display/ws` off authenticated `/api/ws`, Desktop Take over / Hand back, install-from-Desktop via the existing sudo card, and `computer_use` refused with `code: human_has_control` while a human holds.

It is **not**:

- Nous-hosted / cloud headed sessions (PTY + WebVNC + CUA on one remote display) — that is #108592 / PER-1430
- hosted **browser** noVNC for login/CAPTCHA — that is #92524
- `DisplayTarget` / `HeadedCloudSessionProvider` from #108878
- a security boundary (docs say this; the lease does not)

The PR title still says `(#92524)`. The body correctly says Related, not Closes. Keep it that way on merge, if this ever merges.

### P1-6 — Takeover + hand-back during approval still clicks

`handle_computer_use` records `admitted` at line 266, then may wait on approval and backend start. The re-check under the call lock is still **holder-only** (`assert_agent_may_act()` at ~291). `_fence()` compares `admitted.epoch` but is invoked **after** `_dispatch` (and, inside dispatch, only on non-input handlers). `_do_click` calls `backend.click` with no fence.

```
Agent admitted at epoch 0
Approval waits
Human acquire → epoch 1, then release → epoch 2
assert_agent_may_act() sees AGENT → backend.click runs
postflight _fence() notices epoch 2 ≠ 0 → human_has_control
```

Existing `test_takeover_during_an_admitted_action_discards_its_result` patches `_dispatch`, so it never proves “no old-generation device op.” `test_computer_use_capture_fence.py` uses call-through persist/spill/aux spies (`leaked==[]`) and patches `_request_approval`; it covers capture/vision, not this click.

Compare `admitted.epoch` **immediately before** `_dispatch` (call `_fence()` there). If it moved, do not start the device op. Keep the postflight compare.

@smfworks independently confirmed the same hole on this SHA and opened **#109508** (`97ce5d5a`, +1 line `_fence()` before `_dispatch`, recording-backend test that does not patch `_dispatch`). That is the right patch. It is **not** on this HEAD. Cherry-pick into 108914; do not treat 109508 as a second desktop stack.

Tek’s third-round comment (“every legitimate finding is fixed at `d65af42`”) overclaims. The PR body’s “epoch ordering” row is the Desktop `display.status` rollback, not this path.
